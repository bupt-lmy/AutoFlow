# 优化结果归档格式

报告正文必须使用中文。命令、代码符号、文件路径、URL、模型名、各类 ID 和原始错误片段保持原文。每次执行都在文件末尾追加一个完整章节，禁止覆盖、删改或压缩已有章节。

每个执行章节至少包含以下内容：

1. **执行概览**
   - 执行时间（注明时区）、外部 `workflow_id`、产品 `run_id`、内部 `execution_id`。
   - 本次触发输入、最终状态、参与的 Agent，以及报告生成者。
2. **产品提案**
   - 当前问题、仓库或运行态证据、改进目标、受影响范围、不在范围内的内容和主要风险。
   - 原始验收标准必须逐条完整保留，不得只写概括。
3. **审核结论**
   - 审核结果、审核理由、范围与安全性判断、要求补充的内容，以及允许进入编码阶段的条件。
4. **实现记录**
   - Codex 的实现摘要。
   - 逐文件列出变更路径、变更目的、关键逻辑和与哪条需求相关；上游未提供的信息写“未提供”。
   - 记录实现期间出现的偏差、返工和重要取舍。
5. **逐项验收明细**
   - 每条需求单独一行或一个小节，包含：编号、需求原文/来源、状态（通过/失败/阻塞）、验证方法、详细步骤、预期结果、实际结果、证据路径或输出摘要。
   - 不得用无关测试的成功替代该需求本身的验证。
6. **自动化测试记录**
   - 对每条命令记录执行目录、完整命令、退出码、通过/失败数量和关键输出摘要。
   - 失败时保留最相关的错误片段，并说明该失败影响哪些验收项。
7. **浏览器验收记录**
   - 记录 URL、浏览器/视口（可获得时）、按顺序执行的操作、每一步可见断言、实际观察结果和截图路径。
   - 未涉及 UI 时明确写明“不适用”及理由；不能把未执行写成通过。
8. **失败、阻塞与返工建议**
   - 逐项记录复现步骤、错误现象、证据、已确认事实、可能原因（明确标注为推断）和建议的返工动作。
9. **最终结论**
   - 给出通过/失败/阻塞结论、结论依据、未解决问题、残余风险和后续建议。

只有每条验收标准都有直接证据且全部通过时，最终结论才能为“通过”。无法取得证据时写“未验证”或“未提供”，不得编造证据。
